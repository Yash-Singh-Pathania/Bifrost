The scene

Monday morning. New Go engineer.

They open their coding agent and type: "Set me up." The agent searches internal docs. Finds fragments across Confluence, GitHub READMEs, Slack threads, setup scripts. Returns a plausible-looking runbook — except the cert workaround is from 2023, and the VPN step references a tool the team deprecated in January.

Every engineer in this room has lived some version of this. The docs exist. The knowledge doesn't reach the tools.

Scene/02 / 12
The gap

We built search for humans.
Developers work through agents.

Internal search solves a real problem: a human asks a question, reads prose, clicks a citation. But developers don't live in browsers anymore. When the consumer is an agent, prose is the wrong shape.

  • Prose bloats context — every query burns tokens on language the agent re-parses
  • Chat interfaces don't compose — agents can't pipeline a UI into a tool call
  • No structure to traverse — "what depends on Service X" can't be answered from a paragraph
  • Citations are for humans to click, not agents to act on
Gap/03 / 12
The problem with retrieval

Relational questions break search.

Internal search — and any RAG system — answers questions when the answer lives inside a single retrieved chunk. But the questions agents ask are relational.

Traversal

"What services does the auth middleware depend on?"

Requires walking a dependency graph, not searching a paragraph.

Sequencing

"What's the setup order for local dev?"

Requires sequencing knowledge spread across ten documents.

Joining

"Which teams own the services in this call chain?"

Requires joining entity types RAG treats as unrelated text.

A compiled wiki makes relationships first-class. Retrieval only finds them by luck.

Shift/06 / 12
The mental model

Think of it as a compiler.

Raw documentation is source code — human-readable, scattered, full of implicit context. This system compiles it into a structured artifact that agents can execute against.

// source Confluence pages, READMEs, Slack threads, runbooks // compiled output Typed entities: Service, Tool, Procedure, Policy With edges: depends_on, owned_by, prerequisite_of Versioned. Deterministic. Instantly queryable.

LLM reasoning happens once at compile time. Every query after that is a cheap structured lookup.

The interface

Any agent. Any tool.

The query layer speaks MCP — an open protocol any coding assistant can consume. Today: Claude Code, Cursor, Copilot. Tomorrow: whatever replaces them. The wiki doesn't care.

Interface/09 / 12
Why it compounds

Three flywheels.

Demand

Agent pull

Human-maintained wikis die because humans route around bad docs — Slack a colleague, guess, move on. Agents can't. As agent-mediated development grows, pull on this wiki grows with it.

Signal

Compile feedback

Every failed lookup is a signal. Queries that return nothing reveal coverage gaps. Stale entities trigger re-compilation from source. The wiki learns what it's missing.

Inertia

Source gravity

Once a doc is in the compile pipeline, keeping it current is cheaper than letting it rot — the eval harness catches drift automatically. Teams that contribute once stay connected.

Flywheels/10 / 12
Where we start

Pilot — Go engineer onboarding.

Low regulatory risk. Concrete eval questions. High agent demand. Pain everyone recognises.

01

Scope & Schema

Inventory sources. Define entity types: Tool, Environment, Procedure, Policy, Service. Curate eval questions.

02

First Compile

Manual ingest to validate schema against real docs. Start small — ~100 entities. Fix what breaks.

03

Automation

Webhooks from Confluence and GHE trigger incremental recompile. MCP server behind VPN. Eval harness gates every promotion.

04

Pilot Use

Onboard the next Go engineers entirely through the agent. Measure time-to-first-PR. Iterate on coverage gaps the harness reports.
